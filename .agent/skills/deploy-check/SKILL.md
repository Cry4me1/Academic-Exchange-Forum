# vibe-gate 部署后质检与线上巡检 (deploy-check)

本技能指导在生产环境部署完成（如执行 `vercel --prod`）后，或上线前回归阶段，自动化使用 `vibe-gate` 执行全方位站点安全与页面健康质检。

---

## 1. 适用场景与触发时机

### 自动化触发场景（AI 主动触发 / “AI 自己想起来”）
- **生产部署后即时质检**：在执行了 `vercel --prod` 或生产构建发布命令后，AI 必须主动识别并立即执行部署后质检。
- **用户口语化巡检**：当用户提到“线上质检”、“部署完成了帮我看看”、“扫一下线上”、“检查论坛线上质量”时自动激活。

### 显式触发场景（用户明确指令 / “你明确要它做”）
- **斜杠命令一键触发**：用户在聊天框输入 `/deploy-check` 时直接运行本工作流。

---

## 2. 标准质检命令

### 2.1 线上站点部署后快速质检（标准命令）
对已发布的生产环境执行全站探测与端到端质检：
```bash
npx vibe-gate https://scholarly.wiki
```

### 2.2 部署前/后源码安全扫描
在项目根目录进行静态凭证分析与代码规则扫描（排查硬编码密钥）：
```bash
npx vibe-gate scan .
```

---

## 3. 6 个扫描维度及其权重

`vibe-gate` 评估体系总分为 100 分，划分为 6 个核心维度：

| 维度名称 | 英文标识 | 权重 | 核心关注点 |
| :--- | :--- | :--- | :--- |
| **安全头** | Security Headers | **25%** | CSP (内容安全策略)、HSTS、X-Content-Type-Options、X-Frame-Options、Referrer-Policy 等 HTTP 标头配置 |
| **密钥暴露** | Secret Exposure | **20%** | 前端 JS/HTML 打包资源中是否泄漏 API 私钥、数据库凭据、JWT Secret、内部服务 Token |
| **认证覆盖** | Auth Coverage | **20%** | 受保护路径的前端路由守卫完整性、未授权 API 端点访问控制、鉴权回退重定向有效性 |
| **页面健康** | Page Health | **15%** | 状态码 (200 OK)、首屏 JS 运行时错误 (Console Errors)、Broken Links、网络资源请求失败 |
| **混合内容** | Mixed Content | **10%** | HTTPS 页面中是否存在未加密的 HTTP 脚本、样式表、图片或 WebSocket 资源 |
| **SSL/TLS** | SSL / TLS | **10%** | 证书有效期、握手协议版本（TLS 1.2+）、证书颁发机构授信链与域名匹配度 |

---

## 4. 报告解读与修复优先级

质检报告产出后，必须依照**安全危害等级**自上而下修复，切忌只刷浅层分值：

$$\text{认证覆盖} > \text{密钥暴露} > \text{安全头} > \text{页面健康} > \text{混合内容} > \text{SSL/TLS}$$

1. **P0 · 认证覆盖 (Auth Coverage)**：
   - 越权漏洞与鉴权击穿会直接导致核心用户数据泄漏或篡改，必须最优先阻断并闭环修复。
2. **P0 · 密钥暴露 (Secret Exposure)**：
   - 泄露的凭据一旦被抓取，相当于系统大门洞开，需立即轮换密钥并清理客户端构建资源。
3. **P1 · 安全头 (Security Headers)**：
   - 抵御 XSS、Clickjacking、MIME 混淆攻击的防御基线，权重最高（25%），应在 Edge/CDN 统一补齐。
4. **P2 · 页面健康 (Page Health)**：
   - 影响真实用户可用性与体验，排查 404/500 异常与控制台报错。
5. **P3 · 混合内容 (Mixed Content)**：
   - 规避被现代浏览器直接静默拦截的风险，统一重定向或升级协议。
6. **P3 · SSL/TLS**：
   - 确保证书自动化续签正常与协议配置合规。

---

## 5. Scholarly 论坛专属关注项

针对 Next.js (App Router) + Supabase 架构：
1. **Supabase RLS 策略**：确保数据库所有表启用 RLS，无 `true` 全放行策略。
2. **密钥环境变量隔离**：严禁将 `SUPABASE_SERVICE_ROLE_KEY` 暴露给前端（仅限 Node/Edge 服务端）；前端仅可引用 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 与 `NEXT_PUBLIC_SUPABASE_URL`。
3. **路由守卫拦截**：检查 `middleware.ts` 匹配规则，确保敏感受保护路由未被跳过。

在执行扫描后，向用户汇报时必须提供结构化结果：

```markdown
### 🛡️ 线上质检综合评分：XX / 100（等级：良好 / 需改进 / 风险）

#### 1. 扫描维度详情表
| 维度 | 权重 | 得分 / 状态 | 关键发现 |
| :--- | :---: | :---: | :--- |
| 认证覆盖 | 20% | ⚠️ 存在风险 | 检测到部分路由未配置服务端守卫 |
| 密钥暴露 | 20% | ✅ 通过 | 未发现客户端 Bundle 存在硬编码凭证 |
| 安全头 | 25% | ℹ️ 建议补齐 | 缺少 Content-Security-Policy 标头 |
| 页面健康 | 15% | ✅ 通过 | 页面正常 200 响应，无严重控制台报错 |
| 混合内容 | 10% | ✅ 通过 | 全站资源均采用 HTTPS 加密传输 |
| SSL/TLS | 10% | ✅ 通过 | TLS 1.3 启用，证书有效期充裕 |

#### 2. 按优先级排序的修复建议
- **[P0 · 认证覆盖]**：在 `middleware.ts` 补充对 `...` 路由的拦截与鉴权重定向。
- **[P1 · 安全头]**：在 `next.config.ts` 的 `headers()` 配置中注入 `Content-Security-Policy` 与 `X-Frame-Options`。
```
