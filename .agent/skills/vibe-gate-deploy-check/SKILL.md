# vibe-gate 部署后质检指南

本技能指导在生产环境部署完成（如执行 `vercel --prod`）后，或上线前回归阶段，自动化使用 `vibe-gate` 执行全方位站点安全与页面健康质检。

---

## 1. 适用场景与前置条件

### 适用场景
- **生产部署后即时质检**：执行 `vercel --prod` 或 CI/CD 流水线发布后，即时验证线上版本健康度与合规性。
- **线上巡检与安全扫描**：日常排查域名配置、安全响应头、认证边界与潜在凭据泄露。
- **上线前源码预检**：在构建打包前扫描代码仓库，阻断敏感密钥入库与已知安全隐患。

### 前置条件
- **环境依赖**：Node.js 18+ 环境，已配置 `npx` / `npm`。
- **网络可达性**：扫描机能正常解析并访问目标站点域名（例如 `https://scholarly.wiki`）。
- **权限规范**：严格限定仅对待测人员拥有所有权或被明确授权的资产进行主动探测。

---

## 2. 标准质检命令

### 2.1 线上站点部署后快速质检（标准命令）
对已发布的生产环境进行全站探测与端到端质检：
```bash
npx vibe-gate https://scholarly.wiki
```

### 2.2 部署前源码安全扫描
在项目根目录进行静态凭证分析与代码规则扫描：
```bash
cd 项目路径 && npx vibe-gate scan .
```

---

## 3. 6 个扫描维度及其权重

`vibe-gate` 评估体系总分为 100 分，划分为 6 个核心维度：

| 维度名称 | 英文标识 | 权重 | 核心关注点 |
| :--- | :--- | :--- | :--- |
| **安全头** | Security Headers | **25%** | CSP (内容安全策略)、HSTS、X-Content-Type-Options、X-Frame-Options、Referrer-Policy 等 HTTP 标头配置 |
| **密钥暴露** | Secret Exposure | **20%** | 前端 JS/HTML 打包资源中是否泄漏 API 私钥、数据库凭据、JWT Secret、内部服务 Token |
| **认证覆盖** | Auth Coverage | **20%** | 受保护路径的前端路由守卫完整性、未授权 API 端点访问控制、鉴权回退重定向有效性 |
| **页面健康** | Page Health | **15%** | 状态码 (200 OK)、首屏 JS 运行时错误 (Console Errors)、Broken Links、网络资源请求失败 |
| **混合内容** | Mixed Content | **10%** | HTTPS 页面中是否存在未加密的 HTTP 脚本、样式表、图片或 WebSocket 资源 |
| **SSL/TLS** | SSL / TLS | **10%** | 证书有效期、握手协议版本（TLS 1.2+）、证书颁发机构授信链与域名匹配度 |

## 4. 报告解读与修复优先级

质检报告产出后，必须依照**安全危害等级**自上而下修复，切忌只刷浅层分值：

$$\text{认证覆盖} > \text{密钥暴露} > \text{安全头} > \text{页面健康} > \text{混合内容} > \text{SSL/TLS}$$

1. **P0 · 认证覆盖 (Auth Coverage)**：
   - 越权漏洞与鉴权击穿会直接导致核心用户数据泄漏或篡改，必须最优先阻断并闭环修复。
2. **P0 · 密钥暴露 (Secret Exposure)**：
   - 泄露的凭据一旦被抓取，相当于系统大门洞开，需立即轮换密钥并清理客户端构建资源。
3. **P1 · 安全头 (Security Headers)**：
   - 抵御 XSS、Clickjacking、MIME 混淆攻击的防御基线，权重最高（25%），应在 Edge/CDN 统一补齐。
4. **P2 · 页面健康 (Page Health)**：
   - 影响真实用户可用性与体验，排查 404/500 异常与控制台报错。
5. **P3 · 混合内容 (Mixed Content)**：
   - 规避被现代浏览器直接静默拦截的风险，统一重定向或升级协议。
6. **P3 · SSL/TLS**：
   - 确保证书自动化续签正常与协议配置合规。

## 5. 对 Scholarly 论坛项目的特别提示

针对当前 Next.js (App Router) + Supabase 架构的 Scholarly 学术论坛，重点排查以下风险：

### 5.1 认证覆盖与 Supabase RLS 策略
- **RLS 策略漏配（高危）**：
  - 检查 Supabase 数据库中所有涉及用户资料、论文评论、私信、草稿的表，是否均开启了 `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`。
  - 确保没有留存 `true` 放行的全量匿名策略（如误设 `FOR ALL TO anon USING (true)`）。
- **前端路由守卫绕过**：
  - 重点核对 Next.js `middleware.ts` 中的路径匹配器 `matcher`，确认 `/admin`、`/settings`、`/drafts` 等敏感路由未被过滤掉。
  - 确保客户端组件与服务端组件双层校验，避免仅依赖客户端重定向导致敏感数据随 SSR Payload 泄漏。

### 5.2 密钥环境变量隔离
- 严禁将 Supabase 的 `SUPABASE_SERVICE_ROLE_KEY` 暴露给前端（禁止赋予 `NEXT_PUBLIC_` 前缀）。
- 客户端只能使用 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 和 `NEXT_PUBLIC_SUPABASE_URL`。

## 6. 免费边界与运行机制

- **协议与开源属性**：`vibe-gate` 基于 **MIT 开源协议**，完全免费使用。
- **本地运行与零配额消耗**：
  - 扫描全流程在本地执行，**不调用第三方付费云服务**，**不消耗任何 AI Agent Token 或 API 配额**。
- **首次运行依赖安装**：
  - 工具底层依赖 Headless 浏览器进行深层页面加载与控制台诊断。首次运行 `npx vibe-gate` 时，会自动下载配置轻量级 Playwright Chromium 内核，此为正常现象，耗时通常在一分钟内。

## 7. 失败处理与异常排查

| 异常现象 | 核心原因分析 | 标准处置方式 |
| :--- | :--- | :--- |
| **命令超时** (Command Timeout) | 目标站点冷启动慢、首次 SSR 耗时过长，或网络抖动 | 检查站点可用性，可追加超时参数重试；检查 Next.js 服务端日志是否存在卡死或循环重定向。 |
| **网络不通** (Connection Refused / DNS Error) | 域名 DNS 未生效、解析错误、或被目标环境 WAF 拦截 | 先使用 `curl -I https://scholarly.wiki` 验证连通性；若刚绑定域名，等待 DNS 解析传播后再试。 |
| **目标站点非本人所有** | 试图扫描未授权的第三方外部域名 | **严禁执行！** 严格确认仅扫描拥有所有权或获得明确授权的生产域名及测试环境，非授权探测可能违反网络安全法规。 |

## 8. 输出格式规范

在执行扫描后，向用户汇报的答复应遵循结构化输出：

```markdown
### 🛡️ 线上质检综合评分：XX / 100（等级：良好 / 需改进 / 风险）

#### 1. 扫描维度详情表
| 维度 | 权重 | 得分 / 状态 | 关键发现 |
| :--- | :---: | :---: | :--- |
| 认证覆盖 | 20% | ⚠️ 存在风险 | 检测到部分路由未配置服务端守卫 |
| 密钥暴露 | 20% | ✅ 通过 | 未发现客户端 Bundle 存在硬编码凭证 |
| 安全头 | 25% | ℹ️ 建议补齐 | 缺少 Content-Security-Policy 标头 |
| 页面健康 | 15% | ✅ 通过 | 页面正常 200 响应，无严重控制台报错 |
| 混合内容 | 10% | ✅ 通过 | 全站资源均采用 HTTPS 加密传输 |
| SSL/TLS | 10% | ✅ 通过 | TLS 1.3 启用，证书有效期充裕 |

#### 2. 按优先级排序的修复建议
- **[P0 · 认证覆盖]**：在 `middleware.ts` 补充对 `...` 路由的拦截与鉴权重定向。
- **[P1 · 安全头]**：在 `next.config.ts` 的 `headers()` 配置中注入 `Content-Security-Policy` 与 `X-Frame-Options`。
```
